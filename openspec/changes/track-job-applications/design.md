# 扎口Job · 岗位追踪领域设计

## Context

参考源码中，原型的类型用一个阶段字段表示申请进展，演示模型则把面试轮次与总体进度分开，且要求预留至少一轮面试；原型的更新操作已用版本条件保护写入。扎口Job 可以沿用按岗位识别、按版本核对的思路；新模型还要表达只有链接、零个环节、从二面起步，以及进展和结果并存的情况。

## Goals / Non-Goals

本次形成独立的严格类型 TypeScript 业务模块，输入一份岗位的当前记录和用户动作，即可验证并计算变更。通过该模块的公开入口验收业务场景。Sites 是首要使用环境，开源版需要支持浏览器本地存储，两者可复用模块。

数据与后端提案负责读写接口的传输、原子保存、跨端验证和存储适配。前端提案负责页面、开始页偏好与 PWA。现有原型的数据迁移、整份记录的生命周期管理及邮件接入留在各自议题中。

## Decisions

### 一份申请由稳定标识、资料、有序流程、星标和可空结果组成

每份申请和每个流程节点各有稳定 ID。公司和职位用于识别记录的内容，后续补资料、改职位时沿用原 ID。星标岗位优先展示，同组沿用调用方已有的排序。「已挂」和「已拒」保存在结果字段，清除结果即可重新跟进。若把结果也放入流程，拒绝 Offer 后就须向前查找才能取得真正的最后进展。

| 内容 | 表达方式 |
| --- | --- |
| 岗位资料 | 公司、职位、招聘链接、地点、薪资和纯文本 JD。建档时接受招聘链接，或同时给出公司与职位。薪资首版按用户输入的文本保存，可保留「300 元/天」等表述。 |
| 已投递、OC | 用户登记一次实际进展时追加相应节点。 |
| 笔试 / 测评 | 保存该环节的完成状态及可选截止期限，用户可就地标记完成。 |
| 面试 | 保存用户指定的轮次、待面试或已面状态、可选安排时间。允许首条就是「二面」，轮次名称独立于节点在数组里的位置。 |
| 书面 Offer | 保存收到 Offer 的事实和可选答复期限。期限支持日期或具体时刻，只有日期时保留原日期精度。 |

用有序节点序列表示登记次序，末项直接给出最新进展。只收藏时序列为空。若用预先生成的流程模板或按面试时间排序，都会使中途建档、跳过笔试或更正早期时间产生虚假的进展。

### 以岗位动作作为调用边界

创建申请返回带稳定 ID 的记录。补填资料、切换星标、登记环节、更新指定环节、登记或清除结果、撤回末步，都只改变该动作负责的数据。例如 `scheduleInterview` 接收轮次和安排，`rescheduleInterview` 通过节点 ID 更新原安排，`removeLatestStep` 要求调用方提供期望撤回的节点 ID。UI 和未来的自动化入口将调用这些业务动作。整卡覆盖式保存容易让改期顺带覆盖其他人的进展。

模块返回更新后的单条记录或可区分的业务失败。星标排序及是否结束跟进由记录推导。数据库客户端、HTTP 请求、React 状态和各端 SDK 归调用方或适配器负责。

### 撤回时核对目标，保存时核对版本

1. 调用方带上岗位 ID、看到的末节点 ID 和记录版本。
2. 业务模块核对当前版本与指定末节点，再生成仅移除末项的记录；空链或目标不匹配时返回无法撤回。
3. 保存方以读取时的版本为条件原子提交。若核对后、提交前另一端已经更新，返回版本冲突，调用方读取最新记录再让用户选择。禁止把旧操作自动改为删除新末节点。

单用“删除最后一条”会误删另一端追加的三面；单在页面隐藏中间节点的删除按钮也无法保护其他调用入口。本提案用可控的内存记录验证调用契约，真实适配器的并发写入由数据提案复用同一场景验证。

## Risks / Trade-offs

- 无流程的岗位容易被误标为已投递。保留空序列，以「收藏」表达建档，撤回最后一步也回到这个状态。
- 日期被补成午夜可能改变「当日答复」的含义。分别保存日期与带时区的具体时刻，由展示端负责格式化。
- 旧原型的阶段、示例数据与写入接口各有调用方。业务核心独立引入，本次验收使用手工构造的岗位；未来接入时再按对应入口决定映射与迁移。
