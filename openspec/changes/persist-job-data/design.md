# 扎口Job · 数据与后端设计

## Context

工作区已有 `track-job-applications` 的岗位规则与 17 个验收场景，实施尚未开始。共享模块要提供稳定的岗位及节点 ID、规定顺序的流程、独立申请结果和按版本撤回的动作。本设计使用这些约定，不另建一套阶段枚举。

参考原型已有 D1 条件更新，但首次读取会写入初始化岗位；原版与 Demo 也各有专用表。新的个人实例需要独立的空数据集。原型可以读取 Sites 提供的访问者身份，是否为该实例所有者还要核对可信授权信息。

## Goals / Non-Goals

首版交付同一组业务动作的两种存储实现和一份可双向恢复的备份格式。静态入口默认选 IndexedDB，可由本地静态 HTTP 服务或静态托管提供；Sites 构建选同源 API。选择入口时隔离云端依赖，使静态产物可以零业务后端运行。手机与桌面的页面样式、安装引导及布局编辑交给前端提案。额外部署目标、邮件和云端离线队列均留待后续需求。

## Decisions

### 业务动作共用，按单条岗位提交

页面通过相同的应用入口读取岗位、提交岗位动作、读写开始页偏好、导出及恢复看板。举例：`removeLatestStep` 接收岗位 ID、期望版本和节点 ID；IndexedDB 入口在事务内运行领域动作，Sites 入口将动作发送给服务端，在可信端读取当前岗位并执行同一规则。前端组件和领域模块均不引入平台 SDK。整板序列化仅用于备份。

| 数据 | IndexedDB | 私有 Sites |
| --- | --- | --- |
| 岗位 | 以岗位 ID 为键的对象存储，每条包含版本和完整领域记录 | D1 每岗位一行，ID 为主键，版本可用于条件更新，领域资料与流程保存在按版本定义的 JSON 中 |
| 开始页偏好 | 独立对象存储，保存共用布局和可选手机、桌面覆盖 | 同一实例数据库内保存对应设置。写指定范围时保留其他范围，避免手机改布局覆盖桌面布局 |
| 初始状态 | 首次打开仅建立结构 | 由迁移建立结构，两端的首次列表读取都返回零条岗位 |

静态版在同一 `readwrite` 事务内核对版本、计算动作、更新记录，以事务完成为成功。Sites 在 D1 中按 ID 和期望版本更新并递增版本，只有命中一条才确认成功。全新岗位用稳定 ID 插入且禁止覆盖同 ID 记录。同一请求重送时沿用原记录 ID、目标节点及期望版本，已生效的动作不会再追加一次。冲突后由调用方重新读取再选择动作。保存出错时不切换存储后端。[IndexedDB 事务完成事件](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event)

前端只在启动时选择适配器。开源构建缺省选择本地，Sites 选择 HTTP 适配器；后者把 API 基址集中在一处，未来独立部署后端可复用请求契约。查询返回记录及其版本，变更请求传业务动作和期望版本，成功响应返回实际提交的记录及新版本。导入和导出各用一个整板操作，避免页面自行拼接若干岗位请求。

### 私有 Site 的读写和确认

每份部署使用自己绑定的数据库，由服务端选择目标。所有数据路径（含查询、偏好和备份）在同一入口校验 Sites 可信身份及实例所有者授权。利用私有站点访问控制，将站点范围内的稳定用户 ID 与可信部署配置核对；身份或授权缺失时拒绝。首次访问者、客户端传入的站点 ID、邮箱与备份内容均不能授予所有权。模板只携带代码和迁移。

客户端区分三种结果：服务端确认提交后报告成功；本地事务中止或服务端明确拒绝时报告失败；请求已经发出但失去响应时报告「未确认是否保存，请刷新查看」。重新读取取得当前已提交记录；客户端不缓存成功假象，也不在恢复网络后补传动作。多端验收以第二个客户端主动重新读取为准。

### 两种运行模式共用 v1 JSON

文件顶层使用 `format: "zakoujob-backup"`、`version: 1`、`applications`（岗位数组）和 `preferences`（布局偏好）。空数组是合法备份。每份岗位保留领域定义的全部业务字段、岗位和节点稳定 ID、节点顺序及原有时间精度。并发令牌由目标实例管理；备份携带的是可继续追踪的资料。文件中不包含访问身份、数据库绑定或凭据。

布局保存共用布局以及可选的 `mobile`、`desktop` 覆盖，各自保留显示的模块标识与顺序，并保留「沿用共用布局」与「已单独设置」的区别。模块的显示名称、样式交给前端。导出在一个一致快照中读取全部岗位与偏好。IndexedDB 共用一个跨对象存储的只读事务，D1 的多次读取使用同一事务批次。

### 恢复以一次提交为边界

1. 解析并校验整个信封、版本、领域数据及偏好。检查岗位 ID 唯一、同一岗位内节点 ID 唯一、节点和结果合法、日期与时刻可解析。按已有顺序还原，允许空流程或首条就是二面。报告问题记录或字段，目标尚未写入。
2. 在实际写事务中检查目标的全部岗位（含已结束记录）为零。偏好存在也允许导入。通过后插入所有岗位并用备份替换整组偏好，这也能恢复缺省的端覆盖。
3. IndexedDB 在同一次读写事务内完成计数、插入和偏好写入。D1 采用同一 `batch`，首个写操作做数据库级空板断言，已有岗位时须触发 SQL 错误以中止整批。例如设置恢复专用的写入触发器，在存在岗位时执行 `RAISE(ABORT, …)`。仅预查一次或把影响零行当作成功，会留下并发新增后继续导入的窗口。任一后续写入出错均回滚整批。[D1 事务批处理](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)
4. 仅在事务提交后报告恢复成功。恢复有岗位的备份后重试会命中非空检查；只有偏好的备份重复恢复得到相同内容。若响应丢失，按保存结果未知提示回读。

## Risks / Trade-offs

- 备份只填了日期时，统一转换为 UTC 午夜可能改变答复日。编解码保留日期或具体时刻两种表示，往返验收分别比较。
- 浏览器配额、D1 批次或请求大小有限。超过可处理范围时报错并保持原数据；不拆成多个分别提交的恢复操作。
- 以普通登录态代替实例所有者校验会让私有数据暴露给额外访问者。用两个独立实例和身份测试适配器及所有数据路由；真实站点使用平台身份集成。
- 导入整组偏好可能覆盖空看板已有布局。向前端返回明确的恢复语义，验收覆盖仅有偏好的目标和备份未设置分端布局两种情况。

## Migration Plan

为新产品使用独立 IndexedDB 数据库名及新增 D1 表迁移，保留原型数据。部署前用隔离 D1 和浏览器存储演练建空板、跨端保存和双向恢复；原型数据迁移另行设计。应用回退时保留已写数据与备份文件，不用删除数据库实现回退。
